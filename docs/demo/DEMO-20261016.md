## Preparação local

No backend, crie `.env` a partir de `.env.example` e configure localmente `DATABASE_URL` para um PostgreSQL descartável. Nunca copie credenciais para este documento ou para commits. O compose local usa o serviço `postgres`:

```powershell
cd D:\dev\Process\process-ai-backend
Copy-Item .env.example .env
# Edite .env localmente: DATABASE_URL, credenciais locais e configuração do provider, se aplicável.
npm run db:up
$env:MIGRATION_DATABASE_URL = (Get-Content .env | Where-Object { $_ -match '^DATABASE_URL=' } | Select-Object -First 1) -replace '^DATABASE_URL=', ''
npm run db:migrate
```

Se seu `.env` tiver `DATABASE_URL` entre aspas ou interpolação, defina `MIGRATION_DATABASE_URL` diretamente no terminal em vez de usar a leitura simples acima. Use apenas banco local de demonstração; migrations criam o schema da aplicação.

Configure o modo real no `.env`:

```dotenv
AI_GRAPH_IR_MODE=controlled
AI_PROVIDER=openai-compatible
EXTERNAL_AI_APPROVED=true
EXTERNAL_AI_STRUCTURED_OUTPUT=json-schema-strict
```

Complete `EXTERNAL_AI_BASE_URL`, `EXTERNAL_AI_API_KEY` e `AI_MODEL` de acordo com o provider autorizado. O modo `controlled` usa uma chamada na geração inicial. `AI_GRAPH_IR_MODE=off` volta ao pipeline anterior. `shadow` só registra que a comparação está pendente; não faz chamada duplicada.

## Iniciar

Terminal 1 — backend:

```powershell
cd D:\dev\Process\process-ai-backend
npm run dev
```

Terminal 2 — frontend:

```powershell
cd D:\dev\Process\process-ai-frontend
npm run dev
```

Abra [http://localhost:5173](http://localhost:5173). A API local é `http://127.0.0.1:3334`; confira `http://127.0.0.1:3334/health` antes da apresentação. O frontend já usa essa base por padrão. Se sua configuração divergir, defina `VITE_API_BASE_URL` e `CORS_ORIGINS` para as origens locais correspondentes.

## Roteiro de cinco minutos

1. **Problema (30 s):** explique que a descrição natural será convertida em uma proposta revisável; ainda não é executável nem publicável.
2. **Criar projeto (30 s):** clique em **Novo projeto**, escolha `generic-bpmn2` e crie uma sessão.
3. **Gerar (60 s):** use o prompt sintético abaixo. Mostre a revisão proposta e a indicação de atribuições que ainda exigem configuração técnica.
4. **Inspecionar BPMN (60 s):** mostre funcionário → análise do gestor → XOR “Compra aprovada?”; um ramo segue para o financeiro e o outro termina reprovado.
5. **Inspecionar formulários (60 s):** mostre o campo Material solicitado e o campo booleano Decisão do gestor.
6. **Persistir (45 s):** aceite a revisão e recarregue a página; confirme que a revisão aceita e os artefatos voltam da API.
7. **Fechar (15 s):** destaque validação determinística de referências, tipos e estrutura. Papéis sem vínculo de runtime ficam como pendência; nenhuma integração de negócio é executada.

Prompt sintético R01:

> Um funcionário solicita compra de material, informando o material solicitado. O gestor analisa a solicitação. Se aprovar, o financeiro recebe para providenciar a compra. Se reprovar, o processo termina.

### Contingência claramente simulada

O repositório contém `scripts/demo/graph-ir-approval.fixture.json` e `scripts/demo/start-graphir-simulated-server.ts`. Eles servem somente para QA/browser em um PostgreSQL de teste dedicado e não devem ser apresentados como IA. O servidor fixture recusa banco diferente do endereço de teste `127.0.0.1:55432/processai_v2c1` e usa a porta 3334. Para executá-lo, mantenha o frontend local na porta 5173 e inicie a API fixture em terminal separado:

```powershell
cd D:\dev\Process\process-ai-backend
# Obtenha localmente as variáveis de conexão do container PostgreSQL de teste já provisionado.
$env:DATABASE_URL = 'postgresql://<usuario>:<senha>@127.0.0.1:55432/processai_v2c1'
$env:AI_PROVIDER = 'disabled'
$env:AI_GRAPH_IR_MODE = 'controlled'
$env:PORT = '3334'
node --env-file-if-exists=.env --import tsx scripts/demo/start-graphir-simulated-server.ts
```

Esse modo usa uma fixture imutável e não faz chamadas externas. Não use essa configuração contra um banco de dados real ou compartilhado.

## Limitações para explicar

- A validação do provider real não foi aprovada: seis tentativas sintéticas foram rejeitadas por incompatibilidade de schema HTTP 400. A projeção strict foi corrigida em 15/10 com testes offline aprovados. O único smoke R01 real autorizado foi executado uma vez e falhou com HTTP 400 em `response_format`; não houve retry.
- A geração controlada suporta a projeção atual: nós start/end/tarefa humana/XOR, condições atômicas e generic-bpmn2. Integrações declarativas não são oferecidas nesse caminho.
- Papéis sem vínculo autorizado geram prévia `needs-input`; publicação permanece bloqueada até resolução.
- Refinamentos continuam usando o pipeline ProcessSpec anterior. GraphPatch, FormPatch e chunking não estão implementados.
- É uma prévia revisável: sem publicação, execução BPMN ou efeitos em sistemas de negócio.
